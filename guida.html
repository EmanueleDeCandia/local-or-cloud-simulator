1. Come si usa in 5 passi

  1. Scegli il livello di dettaglio. Se hai solo un'idea di massima (utenti, volumi, modello desiderato, budget, tempi) usa Pre-valutazione rapida (15 variabili). Se hai già misure e quotazioni, compila i tab A–J nel pannello di sinistra.
  2. Descrivi il lavoro come Task (tab B): ogni riga è un tipo di attività con volume giornaliero, token, latenza massima, tool call, TB letti dal DWH. È la base di tutto il calcolo (vedi §3).
  3. Premi Calcola (o aspetta: il ricalcolo è automatico dopo ogni modifica). L'indicatore nell'header mostra il TCO delle due alternative e la variazione rispetto al calcolo precedente.
  4. Leggi le card nell'ordine: perimetro → vincoli eliminatori → tempo per task → dimensionamento → costi → TCO → scenari → congruenza dell'utilizzo → sensitività → fit → input → raccomandazione.
  5. Documenta le fonti. In testa a ogni tab puoi indicare fonte/quotazione, data e confidenza: compaiono nella tabella input finale (card 13b) e nel grafico di confidenza. Esporta il JSON per archiviare la valutazione.
I valori predefiniti sono ipotesi dimostrative, non prezzi di listino. Ogni campo che modifichi diventa dato. Puoi scrivere i numeri all'italiana (0,35, 45.000).

2. Fase 1 (pre-valutazione) e Fase 2 (analisi completa)

Fase 1 chiede 15 variabili decisionali (caso d'uso, utenti, task/giorno, picco/media, crescita, parametri del modello, gap di qualità, sensibilità dati, TB di dati, n. integrazioni, budget, orizzonte, scadenza, capacità IT interna, beneficio annuo). Con euristiche documentate le traduce nei ~150 input della Fase 2 e usa lo stesso motore: perciò i risultati sono coerenti e tutte le card si popolano. Restituisce un verdetto di orientamento (vincoli → economia → fit), l'infrastruttura stimata e uno scorecard 0–5.

Fase 2 è l'analisi disaggregata: puoi correggere ogni singolo input generato dalla Fase 1 (i tab di sinistra sono già compilati) sostituendo le euristiche con misure, benchmark e quotazioni reali.

3. Il catalogo Task (tab B) — il cuore del calcolo

Un task è un tipo di lavoro che il sistema AI svolge (una conversazione, l'analisi di un documento, un report). Ogni riga alimenta direttamente il motore; aggiungere, modificare o eliminare una riga ricalcola tutto.

5. Formule principali

Tempo per task

decode_tok/s = banda_GPU × MBU × TP × (1 − penalità·(TP−1)) ÷ byte_pesi_attivi prefill_tok/s = TFLOPS × MFU × TP × (…) ÷ (2 × parametri_attivi) TP = ceil((pesi + KV_task_più_lungo + overhead) × (1+margine) ÷ VRAM_GPU) tempo_task = input ÷ prefill_tok/s + output ÷ decode_tok/s + tool_call × latenza_media cloud = TTFT + input ÷ prefill_API + output × TPOT + tool_call × latenza_media

Dimensionamento GPU

GPU·s/task = (prefill + decode ÷ batch) × TP gruppi_picco = Σ_interattivi(n/gg × quota_ora_punta × GPU·s) × picco_stagionale × crescita_fine_orizzonte ÷ 3600 ÷ TP gruppi_batch = Σ_batch(n/gg × GPU·s) ÷ (ore_fuori_punta × 3600) ÷ TP gruppi = ceil(max(picco, batch) ÷ (1 − contesa_DWH)) + failover + test GPU_totali = gruppi × TP (+ GPU DWH dedicate)

DWH

GB/s_richiesti = TB_task × 1000 ÷ secondi_obiettivo × concorrenza × pruning nodi_locali = ceil(GB/s_richiesti ÷ GB/s_per_nodo) cloud = min(TB_anno × €/TB, slot_picco × €/slot-h × ore_punta × giorni)

Economia

API = Σ token × prezzo (input · cached · output · long-context ×k) × sconto_batch(quota non interattiva) local_TCO_NPV = CAPEX + Σ_t (OPEX_t + refresh_t) ÷ (1+r)^t − residuo ÷ (1+r)^H cloud_TCO_NPV = setup + Σ_t OPEX_t ÷ (1+r)^t EAC (costo annuo equivalente) = TCO_NPV × r ÷ (1 − (1+r)^−H) TCO_corretto = TCO_NPV + mesi_go-live × costo_ritardo_mese valore_netto = beneficio_attualizzato × pass_rate − TCO_corretto energia = kW_medi × ore × PUE × €/kWh

7. Glossario

Open-weight
modello i cui pesi sono scaricabili ed eseguibili in proprio; non necessariamente open source: verificare la licenza
Cloud + API
l'applicazione usa il modello tramite API gestita dal provider, che sostiene GPU e serving; il cliente paga per token
Token
unità di testo (~0,75 parole in inglese, meno in italiano) con cui si misurano input, output e prezzi
Prefill
elaborazione del prompt in un colpo solo; limitata dal calcolo (TFLOPS); determina il TTFT
Decode
generazione token per token; limitata dalla banda di memoria perché rilegge tutti i pesi a ogni token
TTFT
Time To First Token: attesa prima del primo token di risposta
TPOT
Time Per Output Token: ms tra un token e il successivo (40 tok/s ≈ 25 ms)
KV cache
memoria GPU che conserva chiavi/valori dell'attenzione per ogni token di contesto; cresce con contesto × richieste concorrenti
VRAM / HBM
memoria della GPU; deve contenere pesi + KV cache + runtime
Tensor parallel (TP)
suddivisione di un modello su più GPU quando non entra in una sola; ogni "unità" scalabile è il gruppo di TP GPU
Batch (continuous batching)
servire più richieste insieme nel decode: aumenta il throughput aggregato quasi linearmente finché la KV cache lo consente
MBU / MFU
efficienza reale rispetto a banda / calcolo teorici
Quantizzazione
riduzione dei bit per peso (16→8→4): meno memoria e decode più veloce, possibile lieve perdita di qualità
MoE
Mixture of Experts: solo una frazione dei parametri (attivi) lavora per ogni token
SXM / PCIe / NVL
form factor GPU: SXM (server dedicati, NVLink, TDP alto), PCIe (schede standard), NVL (coppie PCIe con bridge NVLink)
TDP
potenza massima della GPU in watt; il consumo medio è TDP × utilizzazione
PUE
Power Usage Effectiveness: energia totale del data center ÷ energia IT (1,5 = +50% per raffreddamento ecc.)
Utilizzazione GPU
quota di tempo in cui le GPU installate lavorano davvero; sotto il 20–30% il locale paga hardware fermo
Picco / media
rapporto tra carico massimo e medio: il locale è dimensionato sul picco, il cloud paga la media
Tool call
chiamata dell'agente a un sistema esterno (ERP, catalogo, CRM, pagamento) per leggere dati o eseguire azioni
Cached input
parte di prompt identica tra chiamate, fatturata a prezzo ridotto dai provider
Long context
prompt oltre una soglia (tip. 200k token) fatturati a prezzo maggiorato
Batch API
elaborazione differita (ore) a prezzo scontato (~50%), adatta ai task non interattivi
Rate limit
massimo token/min o richieste/min del tier API contrattuale
DWH / lakehouse
piattaforma analitica; fatturata in cloud per TB scansionati (on-demand) o per capacità (slot-ora)
Pruning
riduzione dei dati letti grazie a partizioni, indici, clustering
Vector DB / embedding
indice di vettori per il retrieval (RAG); dimensione = vettori × dimensioni × 4 byte × overhead
TCO
Total Cost of Ownership: tutti i costi sull'orizzonte, per un end-state completo e funzionalmente equivalente
NPV
valore attuale netto: flussi futuri scontati al tasso r
EAC
costo annuo equivalente: il TCO NPV trasformato in una rata annua costante
Costo del ritardo
valore perso per ogni mese di attesa prima del go-live
Break-even / congruenza
volume a cui i costi delle due alternative si eguagliano; la card 10 lo calcola ricalcolando l'intero modello
Sensitività (tornado)
variazione del risultato per ±20% di ciascun input, ordinata per impatto
Vincolo eliminatorio
condizione che esclude un'alternativa a prescindere dal costo
Fit
adeguatezza qualitativa (1–5) su fattori non monetizzabili, tenuta separata dal TCO
Dato / ipotesi
valore inserito dall'utente vs valore predefinito del simulatore da confermare
FTE
Full Time Equivalent: persone-anno a tempo pieno
PCI-DSS
standard di sicurezza per chi tratta dati di carte di pagamento; amplia il perimetro di audit in locale
N+1 / failover
capacità aggiuntiva per continuare a servire in caso di guasto
RTO / RPO
tempo massimo di ripristino / perdita massima di dati accettabile
Coding agent
strumenti AI che accelerano sviluppo: applicati simmetricamente alle attività automatizzabili di entrambe le alternative

9. Limiti e buone pratiche

  • Le stime di prefill/decode sono fisiche (banda, FLOPS, efficienze): sostituiscile con un benchmark misurato appena possibile (campo "throughput misurato").
  • Su contesti ≥ 100k token l'attenzione quadratica aggiunge tempo non modellato (+30–100%): valuta chunking/RAG.
  • Il batch è lineare fino al massimo indicato con efficienza 85%; oltre ~128–256 richieste il decode diventa compute-bound.
  • La contesa DWH/GPU co-locata è una quota fissa: nella realtà dipende da schedulazione e PCIe/NVMe.
  • Non confrontare il prezzo di una scheda con quello di un server: usa quotazioni complete (chassis, CPU, RAM, rete, supporto) e indica form factor, IVA, data e fonte.
  • Misura la qualità dei due modelli sullo stesso eval: il gap di qualità è quasi sempre tra le tre variabili dominanti.
  • Economia, fit e confidenza restano su assi separati: non sommarli in un unico punteggio.
